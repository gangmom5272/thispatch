## 2. ERD 안에서 성능을 뽑는 요령 (컬럼 없이 해결)

1. **소제목**: `patch_chunk.text` 가 `title: … | text: Context: <소제목>\nChange: <본문>` 형식이므로 화면 표시·그룹핑은 파싱으로 충분. 별도 컬럼 불필요.
2. **대상 이름·속성·수치·조건**: DB 에 없지만 `patch_change.evidence_quote` 에 문장 원문이 있다. 화면 3 비교는 Qwen 에 원문 문장을 주면 슬롯보다 오히려 풍부하게 나온다. 구조화 값이 필요해지면 HDFS `/embeddings/qwen_raw` 원본에서 뽑는다.
3. **검색 필터**: `direction_id`·`change_type_id` 만 필수 조건, `target_type_id` 는 가점. ERD 그대로.
4. **패치 주기·후속 패치**: 게임별 `news` 패치 공지 시각 차의 중앙값. 뷰 하나면 된다.
5. **요약·비교 캐시**: 테이블 없음 → 백엔드 메모리/Redis 1일. 시연 규모(게임 수십)면 충분.

## 4. 백엔드·프론트에 넘길 것

- 결과군 경계값(delta_pct ±N%p), 소표본 기준(20건) — 기획 확정 필요
- 화면 03·06 의 "게임별 단어사전" 문구 → "AI 판별" 로 수정
- 02c 리뷰별 키워드 칩은 토픽 태그로 대체(또는 C 응답에서 받기)
- 캐시 키: 요약 `(appid, scope, key)`, 비교 `(plan_hash, gid)` — 백엔드
- `topic` 시드 순서 balance=1 … bm=5, `centroid`·`sim_threshold` 는 NULL 로 두고 사용하지 않음(로지스틱 회귀)

## 6. 로컬 종단 검증에서 나온 검색 SQL 메모 (2026-09-14, Top 50 · 청크 20,618)

- **문장 중복 제거**: 같은 게임이 매 공지에 반복하는 문장(Rocket League "New Tournament Reward items have been added")이 후보 30 중 3개를 차지했다. `patch_chunk.text` 의 Change 부분 해시로 1개만 남기거나, 게임당 상위 N(예 3)으로 제한한다.
- **정렬**: `ORDER BY embedding <=> :q` 유사도 순을 기본으로 두고, `target_type` 일치는 동점 처리·표시(✓)에만 쓴다. 가점을 우선 정렬하면 유사도 14점짜리가 1위에 오는 일이 생겼다.
- **필터 통과율**: '적 체력 감소' 질의에서 30후보 중 direction·change_type 통과 16개. 결과군 3개로 나누면 군당 5건 안팎 → 화면 04 "소표본 해석 주의" 기준(20)은 시연 규모에선 거의 항상 걸린다. 기준을 5로 낮추거나 후보를 50으로 늘리는 결정 필요.
