# 라우트 단위 코드 스플리팅

- 측정일: 2026-09-29 / 기준 커밋: bfbe6ac
- 환경: `pnpm build` → `vite preview`(localhost:4173), 백엔드 없음, Lighthouse 12.6.1
- 횟수: 랜딩 데스크톱 5회, 나머지 3회, 중앙값. 원본 보고서는 `code-splitting/{before,lazy,static}/`에 있고, 표는 `node compare.mjs`로 다시 만들 수 있다.
- 비교안
  - `before`: 모든 페이지를 정적 import(단일 번들)
  - `lazy`: 모든 페이지를 route `lazy`로 분리 — **채택**
  - `static`: 랜딩만 메인 번들에 남기고 나머지 분리

## 문제

- JS가 파일 1개, 1,143.50 kB(gzip 339.94 kB)였고, 빌드 시 500 kB 초과 경고가 났다.
- recharts 계열(약 362 KB, 번들의 31.8%)은 반응 추이 탭 2개 파일에서만 쓰는데 랜딩과 로그인도 모두 내려받았다.
- 랜딩과 로그인에서 내려받은 JS의 약 70%(227~238 KB)를 사용하지 않았다.

## 변경

- `src/router/index.tsx`: 페이지 16개를 route `lazy`로 분리했다. 부모(게임 상세)와 자식(탭) 청크는 라우터가 병렬로 받는다.
- `hydrateFallbackElement`: 첫 진입 때 페이지 청크를 받는 동안 헤더가 있는 앱 셸을 먼저 그린다.
- `RouteErrorBoundary`: 배포로 이전 청크가 사라져 모듈을 못 받으면 1회 자동 새로고침한다. 10초 안에 다시 실패하면 안내와 함께 새로고침·홈 버튼을 보여 준다.
- `nginx.conf`: 새로고침하면 새 청크 목록을 받도록 `index.html`에 `Cache-Control: no-cache`를 붙였다. 해시 파일 `/assets/`는 기존 1년 캐시를 유지한다.

## 분석

- 로그인처럼 첫 화면이 가벼운 페이지는 JS가 58% 줄면서 모바일 LCP가 1.05s(19%) 빨라졌다.
- 랜딩 LCP는 세 안이 비슷했다. LCP 요소는 히어로 `h1`이고, LCP 시간 대부분이 Render Delay였다(모바일 약 6.0s, Load Delay 0).
  - `Reveal`이 히어로를 `opacity-0`에서 페이드인하므로 LCP가 JS 용량보다 등장 연출에 묶인다.
  - Google Fonts CSS(`index.html`)가 렌더링을 막아 모듈 스크립트 실행이 약 230ms 늦어진다. 그 뒤에야 랜딩 청크를 요청하는 순차 대기가 생긴다(데스크톱 +약 30ms).
- `static`은 랜딩 모바일 LCP가 약 0.5s 낮게 나왔지만 n=3이고 데스크톱에서는 차이가 없다. 대신 로그인 등 다른 진입점 JS가 +24 KB 늘어난다. 그래서 `lazy`를 채택했다.

## 남은 과제

- 랜딩 LCP: 히어로 첫 화면 등장 연출이 LCP를 늦추는 문제(디자인 결정 필요)
- Google Fonts CSS가 렌더링을 막는 문제(`preload`, 자체 호스팅 검토)
- 반응 추이 탭 진입 시 청크 → 데이터 순차 요청(route loader에서 쿼리 미리 받기)
